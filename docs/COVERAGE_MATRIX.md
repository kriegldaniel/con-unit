# Coverage matrix: ConUnit, Dockle and the Anchore CIS pack

Generated by `go run ./tools/crosscheck coverage -md docs/COVERAGE_MATRIX.md`. Do not edit by hand: a test fails when this file differs from the generator output. The same data produces `table_coverage.tex` (label `tab:coverage`).

## What it compares

Every check of the ConUnit hardening profile (`PACK-CONUNIT-HARDENING`, 17 checks) and of the planned `lint` pack (`PACK-IMAGE-LINT`, 16 checks) against every checkpoint of Dockle and every control of the Anchore CIS policy pack. A row is a property. For each row the matrix says whether ConUnit and the other tool both check it (overlap), only ConUnit does (ConUnit-only), only Dockle evaluates it (Dockle-only) or only the Anchore pack has a control for it (Anchore-only). `neither` marks a property that another tool names but does not evaluate while ConUnit has no check either. `overlap, not comparable` marks a property that both tools address but that the cross-check on archives cannot compare.

The page lists ten controls. The rule bodies of the pack are delivered to customers and are not public, so the Anchore column is a judgement from the control texts. Control titles are described in our own words.
- ConUnit: the rule catalog of this repository (`pkg/conunit/rules.go`, `pkg/conunit/packs.go`) for the hardening profile. For the `lint` pack, the member list and the eight new checks are taken from `docs/INTERFACE_V2.md` section 3. A test compares the lists here with the pack.
- Dockle checkpoints of the form CIS-DI-00NN carry the number NN of the control in section 4 of the CIS Docker Benchmark: the Dockle checkpoint list and the Anchore control list give the same titles in the same order. The numbers of the Anchore pack are those of the Docker Benchmark 1.8.

Notes on single rows:

- SPEC-03: Dockle shares CIS-DI-0010 between the environment part and the file-name part.
- FS-06: ConUnit reads file content, Dockle matches file names.
- FS-12: same file-name lists as Dockle; Dockle has no fixture exemption.
- FS-08: the control text of the Anchore pack names secrets in Dockerfiles, not account passwords.
- SPEC-13: Dockle reports DKL-DI-0006 only for an image name, never for an archive, so the pair is not comparable in the cross-check.
- FS-01: ConUnit checks the resulting filesystem, Dockle judges the recorded commands.
- SPEC-05: ConUnit reads declared ports, the control concerns ports mapped at run time.
- SUP-02: verifies a signature with a configured trust policy; it is not the content-trust setting of CIS-DI-0005.
- CIS-DI-0002: Dockle documents content trust under this code but no code emits it; the Anchore control needs a site configuration.
- CIS-DI-0003: Dockle documents it as not supported; the Anchore control needs a site configuration; ConUnit has such checks outside both packs.
- CIS-DI-0004: Dockle documents it as not supported and points to a vulnerability scanner; ConUnit has no vulnerability check.
- CIS-DI-0005: Dockle reads DOCKER_CONTENT_TRUST of the scanning host, not the image, so the checkpoint is excluded from the cross-check.
- CIS-DI-0011: Dockle documents it as not supported; the Anchore pack does not list control 4.11.

## What the matrix shows

- Hardening profile: 7 of the 12 static checks (tier 1 and 2) have a Dockle counterpart (SPEC-01, CIS-4.6, FS-04, SPEC-07, SPEC-03, FS-06, FS-08). 5 have none (SPEC-05, SPEC-06, FS-05, FS-09, FS-07). The other 5 checks of the profile are tier 3 and tier 4 checks (SUP-02, EXEC-01, EXEC-02, EXEC-04, EXEC-07) and have no counterpart in Dockle or in the Anchore pack. This answers the statement of an external review that Dockle covers roughly 7 of ConUnit's 11 static checks: the matrix counts 12 static checks in the profile where that review counts 11, and 7 of them overlap.
- Dockle documents 20 checkpoints: 11 CIS-DI, 6 DKL-DI and 3 DKL-LI. Of the 11 CIS-DI checkpoints, 7 have a code path in Dockle 0.4.15 and the rest are documented without one or as not supported. This second "7 of 11" is a fact about Dockle, not about ConUnit, and is not the figure of the external review.
- Image-level checkpoints: Dockle evaluates 15 checkpoints from the image (CIS-DI-0001, CIS-DI-0006, CIS-DI-0007, CIS-DI-0008, CIS-DI-0009, CIS-DI-0010, DKL-DI-0001, DKL-DI-0002, DKL-DI-0003, DKL-DI-0004, DKL-DI-0005, DKL-DI-0006, DKL-LI-0001, DKL-LI-0002, DKL-LI-0003). With the lint pack, every one of them has a ConUnit check: 15 of 15 are covered (uncovered: none).
- Not comparable from an archive: SPEC-13. Dockle evaluates DKL-DI-0006 only when it receives an image name, so the cross-check of this work cannot compare it, although the property is covered.
- Excluded checkpoints: CIS-DI-0002, CIS-DI-0005. CIS-DI-0005 reads the DOCKER_CONTENT_TRUST variable of the scanning host, not the image. CIS-DI-0002 is documented as content trust and has no code path, so it is never emitted. Neither is an image-level checkpoint.
- Checkpoints that Dockle documents as not supported and that ConUnit has no check for: CIS-DI-0003, CIS-DI-0004, CIS-DI-0011.
- Anchore pack: 10 controls. ConUnit has a check for 7 of them in the two packs (4.1, 4.6, 4.7, 4.8, 4.9, 4.10, 5.8). No ConUnit check addresses 4.2, 4.3, 4.4.
- Checks that neither Dockle nor the Anchore pack has a counterpart for: SPEC-06, FS-05, FS-09, FS-07, SUP-02, EXEC-01, EXEC-02, EXEC-04, EXEC-07. The tier 3 checks among them start the image; Dockle and the Anchore pack only read it.
- Checkpoints that only Dockle evaluates: CIS-DI-0005. They concern the scanning host and are excluded from the cross-check.

## Limits

- The matrix compares what the checks are designed to find. It says nothing about how often two checks agree on real images; that is the cross-check (`crosscheck.json`, `tab:crosscheck`).
- Overlap means the same property, not the same implementation. Where the implementations differ on purpose, `discordances.csv` of the cross-check states the difference.
- The Anchore column rests on ten control texts. A pack rule that is stricter or looser than its control text is not visible here.
- The Dockle catalog is that of one release. A later release can add or change checkpoints.
